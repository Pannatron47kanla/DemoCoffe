ภาพรวม

ระบบนี้ทำอะไร และให้ใครใช้

ร้านกาแฟหลายกิจการและหลายสาขาใช้ตู้สั่งเครื่องดื่มแบบจอสัมผัสร่วมกันบนแพลตฟอร์มเดียว ตู้จำลูกค้าประจำจากใบหน้าเพื่อทักทาย เสนอเมนูสั่งซ้ำ และสะสมแต้ม ส่วนพนักงานรับออเดอร์หน้าร้านผ่าน POS บนแท็บเล็ต ออเดอร์จากทั้งสองทางเข้าคิวเดียวกันของสาขา

ผู้ใช้ระบบมี 4 กลุ่ม ได้แก่ ลูกค้าหน้าตู้ พนักงานและผู้จัดการสาขา เจ้าของกิจการ และทีมแพลตฟอร์มซึ่งเป็นผู้ให้บริการ

เป้าหมายหลัก

  • ตู้ออนไลน์ตลอดเวลาและทำออเดอร์กับ backend โดยตรง
  • ข้อมูลของแต่ละกิจการแยกจากกันเด็ดขาด
  • การจดจำใบหน้าเป็นความสะดวก ต้องไม่ขวางการขาย
  • เป็นไปตาม PDPA เพราะใบหน้าเป็นข้อมูลชีวมิติ
ขอบเขต

สิ่งที่ตกลงแล้ว

หัวข้อข้อสรุปเหตุผลหลัก
โครงสร้างระบบ3 ส่วน: ตู้ (Edge), Cloud backend, เว็บสำหรับร้านแยกหน้าที่ชัดเจน
UI ของตู้เว็บแอปใน Microsoft Edge โหมดคีออสก์ ทำงานร่วมกับ local agent ในเครื่องใช้โค้ดร่วมกับเว็บร้าน และอัปเดตจากเซิร์ฟเวอร์ครั้งเดียว
การทำงานออฟไลน์ตู้ไม่รับออเดอร์ตอนออฟไลน์ แสดงหน้าสำรองแทน ส่วน POS ขายเงินสดต่อได้ออเดอร์จากตู้ต้องคุยกับ backend แต่การขายเงินสดไม่ควรหยุดเพราะเน็ตหรือ VPS ล่ม
การจับคู่ใบหน้าตู้สร้าง embedding แล้วส่งไปค้นหาในคลาวด์ภายใน tenant เดียวจำข้ามสาขาได้ และเก็บข้อมูลชีวมิติที่เดียว
โมเดล embeddingทดสอบ AuraFace เทียบกับ SFace บน N100 จริง แล้วเลือกตัวเดียวทั้งคู่ใช้เชิงพาณิชย์ได้ แต่ความแม่นยำและความเร็วต่างกัน
การแยกกิจการฐานข้อมูลร่วม + tenant_id + row-level security และคีย์เข้ารหัส embedding แยกต่อ tenantแยกข้อมูลทั้งทางเทคนิคและตามกฎหมาย
ที่ตั้งข้อมูลและโฮสต์VPS ขององค์กรในประเทศไทย (ยืนยันที่ตั้งแล้ว) ข้อยกเว้นเดียวคือเสียงสั่งออเดอร์ที่ส่งไป Gemini Live ในสิงคโปร์ใบหน้าและข้อมูลลูกค้าไม่เข้าเงื่อนไขส่งข้อมูลข้ามแดนตาม PDPA
รูปแบบ backendmodular monolith + Postgresยังไม่จำเป็นต้องแยกเป็น microservice
การจดจำข้ามสาขาทำได้ภายในกิจการเดียวกัน ความยินยอมต้องครอบคลุมทุกสาขาลูกค้าได้ประสบการณ์เดียวกันทุกสาขา
การใช้ใบหน้าทักทายด้วยชื่อเล่นที่ลูกค้าเลือก สั่งซ้ำ และสะสมแต้มตัวตนสำรองคือเบอร์โทรและ QR สมาชิก
การชำระเงินตู้: PromptPay QR ผ่านเกตเวย์อย่างเดียวในเฟสนี้ · POS: เงินสดและ PromptPayไม่ต้องต่อเครื่องรูดบัตรหรือเครื่องพิมพ์
คิวบัตรคิวดิจิทัล ไม่พิมพ์บัตรลดอุปกรณ์ที่ต้องดูแลหน้าร้าน
เสียงสั่งและตอบกลับด้วยเสียงแบบ speech-to-speech ผ่าน Google Gemini Live (Vertex AI สิงคโปร์) โดยลูกค้ากดยินยอมก่อนใช้มีเดโมเสียงได้เร็วในเฟส 1 และเป็นตัวช่วยของจอสัมผัส ไม่ใช่ช่องทางเดียว
สถาปัตยกรรม

สามส่วนหลัก คุยกันผ่าน backend เท่านั้น

ตู้และเว็บร้านคุยกับ Cloud backend เท่านั้น ไม่คุยกันตรง ภาพใบหน้าไม่ออกจากตู้ และคลาวด์เก็บเฉพาะ embedding ที่เข้ารหัสแล้ว

ตู้รับคำสั่งจากส่วนกลาง (เช่น เปลี่ยน threshold หรือปิดตู้) ด้วยการ polling ส่วนสถานะคิวที่ต้องอัปเดตทันทีใช้ SSE หรือ WebSocket

Edge

ตู้คีออสก์

ตู้ทำหน้าที่แสดงหน้าจอ จับภาพ และสร้าง embedding เท่านั้น การตัดสินใจทางธุรกิจทั้งหมดอยู่ที่ backend

  • ฮาร์ดแวร์: มินิพีซี Intel N100 (4 คอร์) RAM 7.8 GB SSD 128 GB Windows 11 Pro กล้อง USB และจอสัมผัส ตามที่ตรวจเครื่องจริงแล้ว
  • UI: เว็บแอปเปิดใน Microsoft Edge โหมดคีออสก์ ล็อกเครื่องด้วย Windows Assigned Access โหลดจากเซิร์ฟเวอร์ ปล่อยเวอร์ชันครั้งเดียวถึงทุกสาขา เลือก Edge เพราะ Assigned Access บน Windows 11 Pro ล็อกแบบแอปเดียวได้กับ Edge ส่วน Chromium ทั่วไปมักต้องใช้ Shell Launcher ซึ่งมีเฉพาะรุ่น Enterprise/Education ทดสอบในเฟส 1
  • Local agent: บริการในเครื่องที่เป็นเจ้าของกล้อง ไมโครโฟน ลำโพง ถือโทเคนประจำตู้ และคุมอุปกรณ์ต่อพ่วง UI เรียกผ่าน localhost โดย agent ตรวจ Origin ทุกคำขอและใช้ secret ที่ผูกกับหน้า UI เพื่อไม่ให้หน้าเว็บอื่นในเครื่องเรียกได้ และต้องทดสอบกฎ Private Network Access ของเบราว์เซอร์
  • Face service: ตรวจจับ จัดตำแหน่ง ตรวจคุณภาพ และสร้าง embedding แล้วส่งเฉพาะเวกเตอร์ขึ้น backend ภาพใบหน้าอยู่ในหน่วยความจำเท่านั้น ไม่เขียนลงดิสก์
  • หน้าจอสำรอง: local agent เสิร์ฟหน้าสำรองจากในเครื่อง และ watchdog สลับไปหน้านี้เมื่อโหลด UI จากเซิร์ฟเวอร์ไม่ได้หรือ heartbeat ล้มเหลว หน้านี้ให้ลูกค้าติดต่อพนักงาน และปิดการสั่งซื้อจนกว่าจะกลับมาออนไลน์
  • ความเสถียร: watchdog เปิดแอปใหม่เมื่อค้าง รีโหลดหน้าวันละครั้งตอนร้านปิด และปิดคีย์ลัดของ Windows

ตู้รับชำระผ่าน PromptPay QR อย่างเดียว ใบเสร็จและบัตรคิวเป็นแบบดิจิทัล จึงไม่ต้องต่อเครื่องรูดบัตรหรือเครื่องพิมพ์ ถ้าอนาคตต้องต่ออุปกรณ์ที่มีแต่ SDK สำหรับ Windows ให้ครอบ UI เดิมด้วย WebView2 โดยไม่ต้องเขียน UI ใหม่

Face recognition

ระบบจดจำใบหน้า

ทั้งสองโมเดลใช้ pipeline เดียวกัน ต่างกันเฉพาะขั้นสร้าง embedding เพื่อให้เปรียบเทียบได้ยุติธรรม แล้วเลือกจากผลทดสอบบนเครื่อง N100 จริง

ขั้นตอนบนตู้

  1. ตรวจเจอใบหน้าที่ใหญ่พอจึงเริ่มประมวลผล YuNet ตรวจจับและจัดตำแหน่งใบหน้า
  2. Quality gate ตรวจความเบลอ ขนาด และมุมหน้า
  3. สร้าง embedding ผ่าน interface เดียว embed(aligned_face) -> vector สลับโมเดลด้วยไฟล์ config
  4. ถ่ายหลายเฟรมแล้วเฉลี่ย embedding ยอมรับว่าเป็นคนเดิมเมื่อคะแนนเกิน threshold ติดกัน 2 ครั้ง และคะแนนอันดับ 1 ต้องห่างจากอันดับ 2 เกินระยะที่กำหนด ถ้าใกล้กันให้ถือว่าจำไม่ได้
  5. ส่งเฉพาะ embedding ไป backend ค้นหาภายใน tenant เดียว ถ้าช้าเกินราว 1.5 วินาทีให้ข้ามไปสั่งตามปกติ

แผนทดสอบ

  • ผู้ทดสอบอย่างน้อย 50 คน อย่างน้อย 3 เงื่อนไข เช่น หน้าตรง หน้าเอียง และแสงต่างกัน
  • วัด FAR, FRR, EER เวลาต่อใบหน้า (เฉลี่ยและ p95) และ RAM ที่ใช้บน N100
  • เกณฑ์เลือก: ถ้า AuraFace ช้ากว่า 0.5 วินาทีต่อใบหน้า หรือแม่นกว่า SFace ไม่ชัด ให้เลือก SFace
  • จูน threshold แยกต่อโมเดล และปรับตามขนาดฐานข้อมูล เพราะโอกาสจำผิดคนเพิ่มตามจำนวนคน
  • embedding ทุกตัวเก็บ model_id และจำนวนมิติไว้ด้วย เพราะเทียบข้ามโมเดลกันไม่ได้
Cloud

Cloud backend และโครงสร้างบน VPS

Backend เป็นที่เดียวที่มี logic ธุรกิจ การแยก tenant และการกำหนดสิทธิ์ผู้ใช้ เริ่มด้วย modular monolith + Postgres

  • โมดูล: Store services (เมนู ออเดอร์ สต็อก สมาชิกและแต้ม) · Face identity (จับคู่ใบหน้าและความยินยอม) · Admin (เครื่องมือ tenant และแพลตฟอร์ม) · Device management (ลงทะเบียนและตั้งค่าตู้)
  • API: ชุดเดียวสำหรับตู้และเว็บ ยืนยันตัวตนสองแบบ คือโทเคนประจำตู้ และบัญชีผู้ใช้ที่มีบทบาทภายใน tenant
  • การแยก tenant: ทุกแถวมี tenant_id พร้อม row-level security ลูกค้าคนเดียวกันที่ใช้สองกิจการเป็นสองเรคอร์ดที่ไม่เชื่อมกัน แอปเชื่อมต่อด้วย role ที่ไม่ใช่เจ้าของตาราง เปิด FORCE ROW LEVEL SECURITY ตั้ง tenant ด้วย SET LOCAL ในแต่ละ transaction และ tenant ของตู้หาจากโทเคนฝั่ง server เท่านั้น
  • ดัชนี embedding: เก็บแบบเข้ารหัสใน Postgres แล้ว backend ถอดรหัสและโหลดเข้าหน่วยความจำแยกตาม tenant ค้นหาแบบ brute-force (ลูกค้า 10,000 คน × 512 มิติ ใช้ราว 20 MB) ไม่ใช้ pgvector ในช่วงแรก เพราะ pgvector ต้องเห็นเวกเตอร์ที่ไม่เข้ารหัส ซึ่งขัดกับการเข้ารหัสต่อ tenant

โครงสร้างพื้นฐานบน VPS

VPS ขององค์กรรองรับช่วงแรกได้ด้วยการติดตั้งแบบเรียบง่าย แต่ต้องดูแลความพร้อมใช้งานและความปลอดภัยเองทั้งหมด

  • รูปแบบ: modular monolith และ Postgres บนเครื่องเดียวหรือสองเครื่อง รันด้วย container มี reverse proxy ทำ TLS
  • สำรองข้อมูล: สำรอง Postgres อัตโนมัติ ทดสอบกู้คืนเป็นประจำ เก็บสำเนาแยกเครื่อง และเข้ารหัสไฟล์สำรอง
  • คีย์เข้ารหัส: คีย์หลักอยู่ใน Vault หรือ OpenBao บนเครื่องแยกจากฐานข้อมูล มีขั้นตอน unseal ใน runbook และผู้รับผิดชอบ ระหว่างที่ยังไม่ unseal การจดจำใบหน้าใช้ไม่ได้ แต่การสั่งซื้อต้องยังทำได้
  • เฝ้าระวังและความปลอดภัย: ตรวจสถานะ VPS ฐานข้อมูล และ heartbeat ของตู้พร้อมแจ้งเตือน ไฟร์วอลล์ จำกัด SSH ปรับแพตช์ และไม่เปิดฐานข้อมูลสู่สาธารณะ
  • ทางขยาย: เมื่อมีหลายกิจการ ค่อยแยกฐานข้อมูล ดัชนี embedding หรือเพิ่มเครื่อง การออกแบบ tenant_id + RLS ทำให้ย้ายได้ภายหลัง

ความพร้อมใช้งาน: ช่วงแรกตู้ทุกตัวพึ่ง VPS จุดเดียว ถ้า VPS ล่ม ตู้ทั้ง 10 สาขาสั่งซื้อไม่ได้ แผนรับมือคือ กำหนด RTO 1 ชั่วโมงและ RPO 5 นาที ข้อเสนอ มี Postgres replica แบบ streaming บนอีกเครื่องพร้อมขั้นตอนสลับที่ซ้อมแล้ว และให้ POS ขายเงินสดต่อได้ระหว่างที่ backend ล่ม

หน้าร้าน

เว็บสำหรับร้านและ POS

เว็บเดียวรองรับทุกบทบาท โดย backend เป็นผู้กำหนดสิทธิ์ ไม่ใช่การซ่อนปุ่มที่หน้าเว็บ ตารางนี้คือสิทธิ์เริ่มต้นที่เสนอ ปรับได้ตามที่เจ้าของกิจการต้องการ

บทบาททำอะไรได้
พนักงานสาขาดูออเดอร์ของสาขา รับออเดอร์ผ่าน POS และเปลี่ยนสถานะคิว
ผู้จัดการสาขาจัดการเมนูของสาขา ดูรายงานและสถานะตู้ของสาขา อนุมัติการยกเลิกหรือคืนเงิน
เจ้าของกิจการเมนูและราคาทุกสาขา รายงานรวม จัดการผู้ใช้และตู้ แก้ข้อความขอความยินยอม และลบข้อมูลลูกค้าตามคำขอ
ทีมแพลตฟอร์มเปิด tenant ใหม่ ดูสถานะตู้ข้ามกิจการ ไม่มีสิทธิ์เข้าถึงข้อมูลลูกค้าและข้อมูลชีวมิติตามปกติ การเข้าถึงเพื่อแก้ปัญหาต้องขออนุมัติและบันทึก audit ทุกครั้ง

POS ทำเป็น PWA ใช้บนแท็บเล็ต เรียก API ชุดเดียวกับตู้ และรับทั้งเงินสดและ PromptPay จึงต้องมีกติกาเงินสด เช่น เปิดและปิดกะ นับเงินสด และให้ผู้จัดการอนุมัติการยกเลิกหรือคืนเงิน

POS ออฟไลน์: เมื่อ backend หรือเน็ตร้านล่ม POS ยังรับออเดอร์เงินสดได้ โดยพักออเดอร์ไว้ในเครื่อง ใช้หมายเลขคิวช่วงสำรองของเครื่องนั้น แล้ว sync ขึ้น backend ด้วย idempotency key เมื่อกลับมาออนไลน์ ระหว่างนั้น PromptPay และตู้ปิดตามเดิม และไม่ใช้การจดจำใบหน้าหรือแต้ม

บัตรคิวดิจิทัล

บัตรคิวออกให้อัตโนมัติเมื่อชำระเงินสำเร็จ แสดงบนจอตู้ จอบอร์ดในร้าน และหน้าเว็บบนมือถือของลูกค้า โดยไม่พิมพ์บัตร ข้อเสนอ ยังไม่ได้สอบกับทีมร้าน

  • การออกคิว: backend ออกหมายเลขคิวต่อสาขาเมื่อได้ webhook ยืนยันการชำระ รีเซ็ตทุกวัน ออเดอร์จากตู้และ POS เข้าคิวเดียวกัน
  • ฝั่งลูกค้า: ตู้แสดงหมายเลขคิวพร้อม QR ที่เปิดหน้าสถานะบนมือถือ ลิงก์เดาไม่ได้ ไม่ต้องล็อกอิน แสดงเฉพาะหมายเลขคิวกับสถานะ
  • ฝั่งร้าน: พนักงานเปลี่ยนสถานะ (รับออเดอร์ กำลังทำ พร้อมรับ) จากเว็บร้านบนจอ POS หรือจอฝั่งทำเครื่องดื่ม
  • จอบอร์ดและการเรียกคิว: เว็บเพจเต็มจอแสดงคิวที่กำลังทำและพร้อมรับ เรียกคิวด้วยคลิปเสียงที่สร้างไว้ล่วงหน้า อัปเดตทันทีผ่าน SSE หรือ WebSocket
  • ความเป็นส่วนตัว: จอสาธารณะใช้หมายเลขคิวเท่านั้น ไม่แสดงชื่อหรือประวัติการสั่ง
เสียง

สั่งและตอบกลับด้วยเสียง

เสียงเป็นตัวช่วยของจอสัมผัส ไม่ใช่ช่องทางเดียว ลูกค้ากดปุ่มเพื่อเริ่มพูด (push-to-talk) แทนการฟังตลอดเวลา เพราะร้านกาแฟมีเสียงรบกวน และการฟังตลอดเวลาเพิ่มภาระด้านความเป็นส่วนตัว

  1. ลูกค้ากดปุ่มพูด ไมโครโฟนบันทึกเสียงสั้นๆ และตัดช่วงเงียบอัตโนมัติ
  2. ถอดเสียงเป็นข้อความด้วยโมเดลภาษาไทย
  3. ตีความเป็นคำสั่งซื้อ จับคู่กับเมนูและตัวเลือกของ tenant แล้วให้ backend เพิ่มลงตะกร้า
  4. พูดตอบทุกครั้ง พร้อมแสดงข้อความบนจอเพื่อให้ลูกค้าตรวจออเดอร์ได้
  5. ยืนยันออเดอร์และจ่ายเงินด้วยการกดบนจอเสมอ

เฟส 1: เดโมเสียงด้วย Gemini Live

เฟส 1 ใช้ Google Gemini Live API ทำ speech-to-speech เพื่อให้มีเดโมสั่งด้วยเสียงได้เร็ว โดยไม่ต้องดูแลโมเดลถอดเสียงและพูดตอบเอง Live API รองรับภาษาไทย (th-TH) รับเสียง PCM 16 kHz และตอบเป็นเสียง PCM 24 kHz ผ่าน WebSocket เงื่อนไขด้านล่างออกแบบให้ใช้ได้ทั้งเดโมและการใช้งานจริง โดยใช้กับลูกค้าจริงได้เมื่อผู้เชี่ยวชาญ PDPA ยืนยันแล้ว

  • การเชื่อมต่อ: UI บนตู้เปิดเซสชัน Live กับ Gemini โดยตรงด้วยโทเคนชั่วคราวที่เซิร์ฟเวอร์ออกให้ ไม่เก็บ API key ไว้ในตู้ เลือกรุ่น native audio ล่าสุดตอนเริ่มทำ
  • การสั่งออเดอร์: Gemini ไม่แก้ตะกร้าเอง แต่เรียกฟังก์ชัน (function calling) ของเซิร์ฟเวอร์ เช่น เพิ่มรายการ ลบรายการ ดูตะกร้า และขอยืนยัน เซิร์ฟเวอร์ตรวจกับเมนูจริงแล้วส่งผลกลับให้ Gemini พูดตอบ จอแสดงตะกร้าตามจริงเสมอ
  • ระบบสั่งออเดอร์แบบง่าย: เซิร์ฟเวอร์เดโมตัวเดียว 1 สาขา เมนูจากไฟล์ JSON มีตะกร้า ออเดอร์ และหมายเลขคิว ยังไม่ใช้ tenant, row-level security หรือ PromptPay จริง ออกแบบ API ให้ใกล้ของเฟส 2 เพื่อให้ UI ตู้ใช้ต่อได้
  • ข้อจำกัด: เซสชันเสียงยาวได้ราว 15 นาที (ปิดเซสชันเมื่อจบออเดอร์อยู่แล้ว) ราคาต่อนาทีและ rate limit ต้องตรวจก่อนเดโม

หน้ายินยอมก่อนสั่งด้วยเสียง: เมื่อลูกค้ากดปุ่มสั่งด้วยเสียงครั้งแรกในเซสชัน ตู้แจ้งสั้นๆ ว่าเสียงจะถูกส่งไปประมวลผลโดย Google นอกประเทศไทย ซึ่งอาจมีมาตรฐานคุ้มครองข้อมูลไม่เท่าไทย ใช้เพื่อรับออเดอร์เท่านั้น และร้านไม่เก็บไฟล์เสียง มีปุ่ม "ยินยอมและเริ่มพูด" คู่กับ "สั่งด้วยการแตะแทน" ขนาดเท่ากัน แยกจากความยินยอมเรื่องใบหน้าและสมาชิก บันทึกหลักฐานรายเซสชัน (เวลา ตู้ เวอร์ชันข้อความ) โดยไม่ผูกกับตัวบุคคล และมีปุ่มหยุดเสียงเพื่อกลับไปแตะจอได้ตลอด

PDPC ยังไม่ประกาศรายชื่อประเทศที่มีมาตรฐานเพียงพอ จึงใช้มาตรการต่อไปนี้ร่วมกับความยินยอม

  1. ใช้ Gemini ผ่าน Vertex AI แบบจ่ายเงินเท่านั้น และยอมรับ Cloud Data Processing Addendum ห้ามใช้คีย์ฟรีจาก AI Studio เพราะ Google นำข้อมูลไปพัฒนาโมเดลและให้คนอ่านได้
  2. เรียกผ่าน endpoint สิงคโปร์ (asia-southeast1) ซึ่ง Google รับประกันที่ตั้งการประมวลผลสำหรับรุ่น Live native audio ห้ามใช้ global endpoint
  3. ปิด data caching และขอยกเว้น abuse monitoring logging เพื่อไม่ให้ Google เก็บข้อมูล
  4. ส่งเฉพาะเสียงกับข้อมูลเมนู ไม่ส่งภาพใบหน้า embedding ชื่อ หรือเบอร์โทร และไม่ใช้เสียงทำ voiceprint
  5. ให้ทนายตรวจว่า SCC ใน CDPA ของ Google ใช้รองรับการส่งออกจากไทยตามประกาศมาตรา 29 ได้หรือไม่ ระหว่างรอ เดโมใช้กับพนักงานหรือผู้ทดสอบที่ยินยอมแล้วเท่านั้น

หลังเดโม: ถ้าผู้เชี่ยวชาญ PDPA ยืนยันเงื่อนไขข้างต้น ใช้ Gemini Live ต่อกับลูกค้าจริงได้ ถ้าไม่ผ่าน ย้ายไปถอดเสียงและพูดตอบบน VPS ตามตัวเลือกด้านล่าง ส่วนเสียงจึงออกแบบหลัง interface เดียวเพื่อสลับได้ และถ้า Google เพิ่มการรับประกันที่ตั้งการประมวลผลใน region กรุงเทพฯ (asia-southeast3) ให้ย้ายไป region นั้น

ทางสำรอง: ถอดเสียงแบบโฮสต์เอง

ตัวเลือกค่าใช้จ่ายเพิ่มข้อดีข้อเสียและความเสี่ยง
บนตู้ (N100)0 บาท ถ้าใช้เครื่องเดิมเสียงไม่ออกจากตู้ ไม่มีความหน่วงจากเครือข่ายแย่ง CPU/RAM กับเบราว์เซอร์และ Face service (RAM ว่างราว 1.7 GB) ต้องอัปเดตโมเดลทุกตู้
บน VPS (CPU) เสนอเริ่มที่นี่0 บาท ถ้ามีกำลังเหลือดูแลโมเดลที่เดียว ตู้เบาลง เสียงอยู่ใน VPS ไทยขององค์กรต้องใช้เครือข่ายทุกครั้ง หลายตู้พูดพร้อมกันต้องดูกำลัง CPU
บน VPS (GPU)ไม่ทราบรองรับโมเดลใหญ่ เช่น Typhoon Whisperต้องสอบถามราคา GPU กับผู้ให้บริการ VPS
Typhoon API (SCB 10X)ฟรีด้วยคีย์ เพดาน 100 คำขอต่อนาทีต่อได้เร็วเสียงออกนอก VPS ต้องอ่านนโยบายความเป็นส่วนตัวของผู้ให้บริการ
Google Speech-to-Text V20.016 ดอลลาร์ต่อนาที (ราว 96 บาทต่อ 1,000 ออเดอร์เสียง ถ้าออเดอร์ละ 10 วินาที)ไม่ต้องดูแลโมเดลเสียงไปนอกประเทศ ต้องเข้ามาตรา 28–29 จึงไม่แนะนำ
  • เริ่มที่ VPS (CPU): ใช้ Typhoon ASR Real-time (114 ล้านพารามิเตอร์ CER 0.0984) ย้ายมาบนตู้ได้ถ้าวัดแล้ว N100 ถอดเสียง 10 วินาทีได้ภายในราว 2 วินาทีขณะ Face service ทำงาน
  • พูดตอบ: สร้างคลิปเสียงล่วงหน้าสำหรับประโยคคงที่และชื่อเมนูของแต่ละ tenant แล้วประกอบประโยค ใช้การสังเคราะห์สดด้วย KhanomTan TTS เฉพาะเมื่อวัดแล้วเร็วพอ
  • ตีความคำสั่ง: เริ่มจากจับคู่ชื่อเมนูแบบ fuzzy และตัวเลือก (ขนาด ความหวาน นม) ก่อน แล้วค่อยพิจารณาโมเดลภาษาขนาดเล็กบน VPS
  • ความเป็นส่วนตัว: ไม่เก็บไฟล์เสียง ถอดแล้วทิ้งทันที และระบุเรื่องเสียงในข้อความแจ้งลูกค้า การส่งเสียงไปนอกประเทศทำได้เฉพาะผ่าน Gemini Live ตามเงื่อนไขด้านบน
  • ฮาร์ดแวร์เพิ่ม: ไมโครโฟนลดเสียงรบกวนและลำโพงที่ตู้ ต้องทดสอบในร้านจริงที่มีเสียงเครื่องบดกาแฟ

ทักทาย สั่งซ้ำ สะสมแต้ม

เมื่อตู้จำลูกค้าได้ ระบบใช้ตัวตนนั้นทำ 3 อย่าง และทุกอย่างมีทางเลือกที่ไม่ใช้ใบหน้า เพราะการจดจำพลาดได้

  • ทักทาย: แสดงชื่อเล่นที่ลูกค้าเลือกเองตอนลงทะเบียน ไม่แสดงประวัติการสั่งเต็มจนกว่าลูกค้ายืนยัน
  • สั่งซ้ำ: เสนอเมนูที่สั่งล่าสุดหรือบ่อยสุด กดยืนยันครั้งเดียว ข้อมูลจากประวัติทุกสาขาในกิจการเดียวกัน
  • สะสมแต้ม: ผูกแต้มกับเรคอร์ดลูกค้าเมื่อชำระสำเร็จ ใช้ได้ทุกสาขาของกิจการ
  • ทางเลือกสำรอง: เบอร์โทรหรือ QR สมาชิกใช้สะสมแต้มได้ทันที การดูประวัติหรือแลกแต้มยืนยันด้วย OTP หรือ PIN
  • การลงทะเบียน: ครั้งแรกที่ตู้ผ่านหน้าขอความยินยอม และผูกกับตัวตนสำรอง เพื่อให้แต้มไม่หายเมื่อต้องลงทะเบียนใหม่ เช่น เปลี่ยนโมเดล

ขอบเขตสิทธิ์ของใบหน้า: ใบหน้าใช้ได้แค่ทักทาย เสนอเมนูสั่งซ้ำ และสะสมแต้ม การแลกแต้มและการดูประวัติการสั่งเต็มต้องยืนยันด้วย PIN เสมอแม้ตู้จะจำหน้าได้ เพราะยังไม่มี liveness และการจดจำอาจจับผิดคน

กฎหมาย

ความปลอดภัยและ PDPA

ใบหน้าเป็นข้อมูลชีวมิติที่ต้องได้รับความยินยอมโดยชัดแจ้ง จึงแยกข้อมูลตามกิจการและเก็บข้อมูลไว้ในไทย

  • บทบาทตามกฎหมาย: แต่ละกิจการเป็นผู้ควบคุมข้อมูล (controller) ผู้ให้บริการแพลตฟอร์มเป็นผู้ประมวลผล (processor) ต้องทำสัญญาประมวลผลข้อมูลกับทุกกิจการ
  • ความยินยอม: แยกต่อ tenant ระบุว่าครอบคลุมทุกสาขา การถอนต้องง่ายเท่าตอนให้
  • ผู้เยาว์: ไม่เปิดให้ผู้เยาว์ลงทะเบียนใบหน้าเพราะตู้ตรวจอายุไม่ได้ หน้าขอความยินยอมให้ยืนยันว่าบรรลุนิติภาวะแล้ว ผู้เยาว์ใช้เบอร์โทรหรือ QR สมาชิกแทน รอผู้เชี่ยวชาญ PDPA
  • การส่งข้อมูลข้ามแดน: เก็บและประมวลผลในไทย ถ้าจำเป็นต้องส่งออก ต้องเข้าเงื่อนไขมาตรา 28–29 (ที่มา)
  • ข้อยกเว้นเรื่องเสียง: เสียงสั่งออเดอร์ส่งไป Gemini Live ที่ประมวลผลในสิงคโปร์ได้ โดยอาศัยความยินยอมหลังแจ้งเรื่องมาตรฐานของปลายทาง ร่วมกับข้อตกลงประมวลผลข้อมูลของ Google (ดูเงื่อนไข) ใบหน้าและข้อมูลชีวมิติยังเก็บและประมวลผลในไทยเท่านั้น รอผู้เชี่ยวชาญ PDPA
  • ระยะเก็บ: face_template ถูกลบอัตโนมัติเมื่อลูกค้าไม่มาใช้บริการ 12 เดือน และมีเมนูลบตามคำขอ รอผู้เชี่ยวชาญ PDPA
  • ตู้: BitLocker, Assigned Access และ ZeroTier เพื่อดูแลระบบจากระยะไกลเท่านั้น ห้ามให้ข้อมูลชีวมิติวิ่งผ่าน
  • ทีมแพลตฟอร์ม: ไม่มีสิทธิ์เข้าถึงข้อมูลลูกค้าโดยปริยาย แต่ในทางเทคนิคผู้ดูแล VPS และ Vault เข้าถึงได้ จึงจำกัดผู้ถือสิทธิ์ ใช้การขออนุมัติเป็นครั้ง และบันทึก audit ทุกครั้ง

ข้อเสนอนี้ไม่ใช่คำปรึกษากฎหมาย ผู้เชี่ยวชาญ PDPA ควรตรวจข้อความยินยอมและสัญญาประมวลผลข้อมูลก่อนเปิดใช้งาน

การดำเนินงาน

ดูแลทุกสาขาจากส่วนกลาง

  • จัดการตู้: ลงทะเบียนทีละเครื่อง ออกโทเคนที่หมุนเปลี่ยนได้ สั่งปิดหรือล้างข้อมูลจากระยะไกล ตั้งค่าต่อ tenant (โมเดล threshold) และส่ง heartbeat กลับโดยไม่มีภาพ
  • ปล่อยเวอร์ชัน: ปล่อยเป็นกลุ่ม สาขาทดลองก่อนแล้วค่อยขยาย ย้อนกลับได้ และตรวจได้ว่าตู้ไหนใช้ UI เวอร์ชันอะไร
  • เน็ตหลุด: ตู้แสดงหน้าสำรองและปิดการสั่งซื้อ POS ขายเงินสดต่อในโหมดออฟไลน์ เจ้าของร้านเห็นสาขาและตู้ที่ออฟไลน์
  • การชำระเงิน: idempotency key ตรวจสถานะย้อนหลัง และรับ webhook จากเกตเวย์
